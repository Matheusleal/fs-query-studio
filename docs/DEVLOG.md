## 2026-08-05 — Fix: worker's console sink was writing to stdout

Caught while starting A.3's stdin/stdout main loop, before it was wired up: `LoggerSetup.build` always sent its console sink to stdout, but Section 7 reserves the worker's stdout exclusively for NDJSON protocol frames. A worker-role logger would have interleaved Serilog console lines into the same stream the host parses as JSON frames — a bug that wouldn't have shown up until real logging volume made a parse failure likely, and would have been confusing to diagnose from the symptom alone.

Fixed by making `LoggerSetup.build` route console output through stderr whenever `processRole = "worker"` (via Serilog's `standardErrorFromLevel`), and added a `logsDirectory` parameter (previously hardcoded to the real `%LOCALAPPDATA%` path) so tests can point the file sink at a temp directory instead of writing into the user's real logs folder on every test run. Two new tests assert the stdout/stderr split and that the file lands where told.

## 2026-08-05 — A.5: execution/evaluate for a whole script

Added `Evaluation.evaluate` in `Execution`: runs a script through the session from A.4 and returns a raw `EvaluationOutcome` (FSI value, captured output/error text, diagnostics, exception) — deliberately not yet the protocol-neutral `ResultEnvelope` from Section 11, which is a later task that will consume this.

The first test run (`printfn "hi"; 1 + 1`, asserting `"hi"` shows up in captured output) failed for a real reason: `FsiEvaluationSession`'s own `outWriter`/`errorWriter` only capture FSI's REPL echo (`"> val it: int = 2"`), not the script's own `printfn`/`Console.Write` calls — those go through `System.Console.Out`, a separate global that isn't automatically redirected just because you passed a custom writer into `FsiEvaluationSession.Create`. Second, unrelated failure surfaced at the same time: the CWD test from A.4 started failing intermittently once a second test module (`EvaluationTests`) existed, because `FsiSession.create`'s `Directory.SetCurrentDirectory` call is process-global and xUnit runs different test classes/modules in parallel by default — two tests each setting a different "current directory" race each other. Fixed with `[<assembly: CollectionBehavior(DisableTestParallelization = true)>]` in a new `AssemblyInfo.fs`, scoped to `Execution.Tests` only (the one test project whose subject mutates process-global state; parallelism elsewhere is unaffected). ## 2026-08-05 — A.6: result projection for Scalar/Text/Table

Filled a gap noticed while re-reading Section 11 for this task: `ResultEnvelope`'s `Output: OutputLine list` field referenced a type that was never actually defined anywhere in the doc. Added `OutputStream`/`OutputLine`, and made explicit that these projection types are protocol-neutral wire shapes belonging in `Protocol` (matching `Diagnostic`'s placement from Section 8) — `Results` produces them, it doesn't own them. Also turned "such as 500 rows" into a concrete named constant, `PreviewRowLimit = 500`.

Added `Projection.project` in `Results`, covering the three kinds in scope: primitives → `Scalar`, strings → `Text`, records → a one-row `Table` (reflection-derived columns), sequences → a bounded `Table` preview. `Object`/`Error`/`NoValue` stay out of scope here, landing with whatever later task actually needs them.

One test failure, `a record projects to a one-row Table...`, initially looked like it might be an ordering bug in the `match`, but turned out to be a real gap in the projection code once isolated: `Microsoft.FSharp.Reflection.FSharpType.IsRecord`/`GetRecordFields` default to public-only reflection, so a `type private Foo = { ... }` — which a `.fsx` script can legitimately write — would silently fall through to the generic `Text` fallback instead of being recognized as a record. Confirmed the diagnosis by temporarily removing `private` from the test's record (test went green), then reverted that and fixed the real cause instead: pass `BindingFlags.Public ||| BindingFlags.NonPublic ||| BindingFlags.Instance` explicitly everywhere a record is inspected. Worth the extra step — the tempting fix (adjust the test) would have shipped a real bug.

## 2026-08-05 — A.7: error projection and wiring execution/evaluate for real

Added `Projection.projectError` (straightforward — `ResultKind.Error` with the exception's message) and, since this task's own test description ("the worker process is still alive afterward") only means something once there's a real request/response round trip through a real worker process, wired `execution/evaluate` as an actual `Handlers.dispatch` case: deserialize `EvaluateParams`, create a fresh `FsiSession` in a fresh temp directory (isolated-by-default per Section 9 — no session persistence across requests yet), evaluate, project to `Error` or the A.6 value-based projection depending on whether the outcome carries an exception.

Hit a genuinely interesting FSI/F# semantics gotcha while writing the "throwing script" test. First attempt used the script `failwith "boom"` and got back the message *"Operation could not be completed due to earlier error(s)"* instead of "boom" — looked like a bug in `Evaluation`. Isolated it with a direct unit test (bypassing JSON/process transport entirely) and got the identical wrong message, which ruled out the integration test's transport as the cause and pointed at FSI itself. The real mechanism: `failwith` has type `string -> 'a` — a *bare* top-level `failwith "boom"` never gets a concrete type, so F#'s value restriction rejects the interaction as a **compile** diagnostic before it ever runs; no runtime exception is ever raised, so of course "boom" never surfaces. Confirmed by annotating a concrete type, `(failwith "boom" : int)`, which executes and throws normally. Kept both as tests: one exercising the realistic case (concretely-typed throw, real message), one as a characterization test documenting the value-restriction trap for anyone who hits it again — flagged as relevant to Milestone B's diagnostics work, since a user could genuinely write a script that's just `failwith "some message"` and would need to see *why* nothing ran, not a generic crash message.

## 2026-08-05 — A.8: host-side worker crash detection and recovery

Before writing this, re-read Section 9's worker-lifecycle diagram to make sure A.3's long-running request loop (one process handling many requests, built for `worker/health`) wasn't actually contradicting the documented model — it says "worker executes one request... host disposes worker after isolated run", which could be read as one-process-per-request. Concluded this describes the *host's isolation policy* for execution specifically (Section 9 is titled "Isolated by Default"), not a constraint on the worker's own request loop — Milestone E's persistent-session mode later reuses that same loop, so the capability needs to exist regardless. Left A.3 as built; scoped A.8 narrowly to what its own test actually asks for: crash detection and recovery, not "always restart after every execute" (that policy question belongs wherever Run (F5) gets wired end to end).

Added `WorkerClient` in `App` (the project Section 4 assigns "worker lifecycle" to): lazily starts a worker process, reuses it across `Send` calls, and — since a healthy worker's request loop never voluntarily closes its own stdout — treats `NdjsonStream.readFrame` returning `None` after a request was sent as unambiguous proof the process died. Returns a structured `worker/crashed` error for that request instead of hanging, and drops the dead process reference so the *next* `Send` starts a fresh one rather than retrying.

Tested against a real spawned process: send a request, kill the process while a second request is in flight, assert the crashed error comes back, then assert a third request gets a new process (different PID). No artificial synchronization needed for "mid-request" timing — the synchronous prefix of `Send` (reusing or starting the process) runs before the task's first real suspension point, so reading `WorkerClient.CurrentProcess` right after calling `Send` reliably reflects the process actually handling that call. Ran the suite three times to rule out a kill-timing race.

## 2026-08-05 — A.9: execution/cancel, cooperative then forced

The biggest single task so far — cancellation genuinely needs concurrency: the worker has to keep reading stdin (for a possible `execution/cancel`) while an `execution/evaluate` is still running, and the host has to correlate responses by `Id` instead of assuming strict request/response ordering, since the cancel's ack can now arrive before the evaluate's real result.

**The cancellation signal.** First attempt: bind a `CancellationToken` into the FSI session via `AddBoundValue` and have the script poll `.IsCancellationRequested`. Failed immediately with a type-check error — `System.Threading.CancellationToken (System.Runtime, ...)` vs `System.Threading.CancellationToken (System.Private.CoreLib, ...)`. Tried a plain `bool ref` next, hit the identical class of error for `System.Boolean`. Root cause, confirmed via a throwaway spike (deleted after): `FsiEvaluationSession` type-checks scripts against *reference assemblies* (compilation facades), while a host-constructed object comes from the *runtime assemblies* actually loaded in the process — different identities for the same nominal type, so `AddBoundValue` can't unify them for anything, not even primitives. The fix that worked: don't inject a value at all — add `--reference:<path-to-Execution.dll>` (the assembly's own already-loaded location) to the FSI session's argv, so a script can call `FSharpQueryStudio.Execution.CancellationSignal.isCancelled()` as an ordinary static member, resolved entirely within FSI's own compilation. No value ever crosses the boundary. `CancellationSignal` is a single mutable flag — sufficient because a worker runs at most one evaluation at a time (see below).

**Concurrency, worker side.** `Program.fs`'s loop now backgrounds `execution/evaluate` specifically via `Task.Run`, immediately looping back to read the next frame — everything else stays synchronous (fast, no need to background). Added a `SemaphoreSlim`-guarded `writeResponse` since the backgrounded evaluate's eventual response and the loop's own synchronous responses now both write to the same stdout. `Handlers.handleEvaluate` gained an `Interlocked.CompareExchange`-guarded busy check: since the worker now *can* receive a second `execution/evaluate` while the first is still running (nothing stops a misbehaving client from sending one), and `FsiSession.create`/`CancellationSignal` both mutate process-global state a second concurrent evaluation would corrupt, a second request while one is in flight gets a structured `execution/busy` error instead of silently racing.

**Concurrency, host side.** `WorkerClient` needed a real rework: a background reader loop now matches every incoming response to its request by `Id` via a `ConcurrentDictionary<string, TaskCompletionSource<...>>`, replacing the old "write then read the next line" assumption from A.7/A.8 (which broke the moment a cancel-ack could legitimately arrive before the evaluate's real result). Added `Cancel(requestId, gracePeriod)`: send `execution/cancel`, await its ack, then race the *original* request's completion against the grace period — if the grace period wins, kill the process and resolve the original caller with a distinct `execution/forciblyStopped` error rather than the generic `worker/crashed` from A.8.

**Tests.** Two full paths, both against a real spawned process: a script polling `CancellationSignal.isCancelled()` in a tight loop stops within the loop iteration (`Scalar` result, value far short of the loop bound, worker still alive afterward); a script that never checks it (`while true do ()`) gets killed after a short grace period and its caller receives `execution/forciblyStopped`. Also proactively added `DisableTestParallelization` to `Worker.Tests` before hitting a flake this time, having already learned that lesson the hard way in `Execution.Tests` (A.5) — `Handlers.handleEvaluate` and `CancellationSignal` mutate the same kind of process-global state.

## 2026-08-05 — A.11: loopback asset host for Monaco

Added `AssetHost` in `Editor`: a plain `HttpListener`-based static file server (no ASP.NET Core — this is Monaco asset serving, not a real web app, and pulling in a full web host for it would be a lot of weight for what it does). `"127.0.0.1"` is the only host literal anywhere in the module, so there's no code path that could ever bind all interfaces. Port is OS-assigned: `HttpListener` doesn't support ephemeral-port prefixes directly, so the standard workaround applies — bind a `TcpListener` to port 0, read back the OS-assigned port, stop it, and immediately reuse that port for the real `HttpListener` prefix.

`resolveAsset` rejects anything that resolves outside `assetsRoot` after `Path.GetFullPath` normalization, and every response carries a restrictive CSP header. The path-traversal test needed care to actually test something: `Uri(baseUri, "../../secret.txt")` would have .NET's own `Uri` combiner collapse the literal `..` segments client-side before the request ever left the process, making the test pass without ever exercising the server's defense. Used percent-encoded `%2e%2e` instead — `Uri`'s dot-segment normalization operates on raw, still-encoded path segments, so encoded dots survive to the server, get decoded by `HttpListener` into literal `..`, and only then hit `resolveAsset`'s check. All four tests (known asset serves, unknown 404s, encoded traversal rejected, loopback-only) passed on the first real run.

## 2026-08-05 — A.15: wire Run (F5) end to end — and a real cancellation bug found along the way

Added the pieces: `Projection.projectWorkerError` (a `WorkerErrorInfo` from a crashed/busy worker reads as `ResultKind.Error`, same as a script-level exception, since the UI needs one shape either way); `ResultViewModel` (`Kind`/`DisplayText`/`Schema`/`Rows`/`IsTruncated`/`ElapsedMs`, applied from a `ResultEnvelope`); `ShellViewModel.RunAsync`, gated by a settable `ExecuteAsync: (string -> Task<ResultEnvelope>) option` — `None` by default so the view model stays constructible and unit-testable without a real worker behind it, wired by the composition root; and `ExecutionService.evaluate` in `App` (the "host service" — builds the `execution/evaluate` request, sends it via `WorkerClient`, and projects whatever came back, including the crash/busy path, into a `ResultEnvelope`).

**Then a pre-existing test (A.9's cooperative-cancellation test) started failing — not from anything in this task, but exposed by running Integration.Tests with more tests in the assembly.** Chased it properly rather than adding a longer sleep:

1. First hypothesis, and genuinely real: `CancellationSignal`'s design (a static field, with scripts calling back into `FSharpQueryStudio.Execution` via a self-referencing `--reference:`) turned out to be *intermittently* broken — `FsiEvaluationSession`'s collectible `AssemblyLoadContext` sometimes loads its own separate copy of an explicitly path-referenced assembly instead of reusing the one already loaded in the process, giving the script's copy of the static field no connection to the one the host mutates. Rebuilt `CancellationSignal` around a sentinel file in the evaluation's working directory instead — OS-level, no assembly identity to get out of sync, and the script now just calls plain `System.IO.File.Exists(".cancel-requested")` with no reference to `Execution.dll` needed at all. Removed the `--reference:` from `FsiSession.create` entirely.
2. That fix alone made the failure worse — 100% reproducible instead of intermittent, which was actually the useful clue: a deterministic failure pointed at a real logic bug rather than remaining an unexplained flake. Root cause: `Handlers.handleEvaluate` set `currentWorkDir` *inside* the `Task.Run`'d background task that runs the FSI evaluation, but the worker's read loop backgrounds that task and immediately goes back to reading the next frame. A freshly started process's ThreadPool needs time to inject worker threads under load, so a client sending `execution/cancel` quickly enough could have it arrive *before* the backgrounded callback had even started — `handleCancel` would see `currentWorkDir = None` and silently no-op, burning the entire grace period until forced termination. Confirmed by comparing against the equivalent in-process `Execution.Tests` version of the same scenario (no subprocess, no threadpool cold-start) — it passed reliably every time, which narrowed the bug to the worker-process path specifically rather than the cancellation mechanism itself.

   Fixed by construction, not timing: split `handleEvaluate` into `beginEvaluate` (synchronous — the busy-check and `currentWorkDir` reservation) and `runEvaluate` (the actual FSI work, safe to background). The worker's loop now calls `beginEvaluate` inline, before it ever returns to reading the next frame, so a subsequent `execution/cancel` is *guaranteed* to observe the reservation — no race window exists to lose, regardless of threadpool timing. Applied the identical fix to `Worker.Tests`' busy-guard test, which had unknowingly relied on the exact same unsound "background it, then `Task.Delay`, then check" pattern.

Re-verified with the same rigor as the original diagnosis: the specific test that had been failing 100% of the time went to 5/5 clean runs afterward, each now taking ~2-3s instead of blowing through the full 15s grace period every time. Then the whole suite, three full runs, all green — 77 tests.

**The stale-response race, specifically.** Backgrounded `analysis/check`/`analysis/hover` in `Program.fs`'s read loop (`Task.Run`, same shape as `execution/evaluate`'s existing backgrounding) — before this, the read loop processed every non-evaluate method fully synchronously, meaning two `analysis/check` requests sent back-to-back could *only* ever complete in send order; there was no way for a genuinely older response to arrive after a newer one, making B.5's guard untestable under real concurrency. Unlike `execution/evaluate`, no busy-slot reservation is needed here — each call builds its own isolated `AnalysisContext` in a fresh temp directory already, so concurrent analysis requests don't share mutable state the way `FsiSession` does.

Chose not to chase literal wall-clock racing for the acceptance test itself, though: awaiting two concurrent requests and hoping the older one *happens* to resolve second would be exactly the kind of timing-dependent flake this codebase has avoided elsewhere. Instead the test deterministically controls response *processing* order — awaits and applies the newer (v2) response first, then awaits and applies the older (v1) response second — which is a faithful real request/response round trip through the same worker, "artificially delayed" in the sense the task names (the test chooses when to apply each response), not a mocked guard check like B.5's own unit test.

Also had to bump the "squiggles" scenario's wait from the debounce window alone (400ms) to 3s — a freshly spawned worker's very first `analysis/check` pays FCS's cold reference-resolution cost on top of the debounce, the same first-call latency A.4's DEVLOG entry already flagged for `FsiSession`.

Full solution: 138 tests, all green (`Worker.Tests` 14, `Ui.Tests` 42, `Integration.Tests` 16 — `MilestoneBAcceptanceTests.fs` new, 3 tests, run 3x to confirm no flake).

## 2026-08-06 — D.6 follow-up: fix a real concurrency bug and CI-cold-runner timeouts surfaced by the first Actions run

## 2026-08-06 — D.7: Windows packaging/installer (WiX Toolset MSI)

Asked which installer technology before starting — WiX, Velopack, or deferring packaging entirely — since it's a real architectural choice (distribution, signing, long-term maintenance) the plan didn't pin down. Chose WiX Toolset (MSI).

Automated test (`PublishedAppTests.fs`, `Category=RequiresPublish`, deliberately excluded from D.6's CI filter alongside `RequiresDocker` — a full self-contained publish plus a real windowed launch is too heavy for every push, and CI's filter got updated to exclude it too): runs a real `dotnet publish -r win-x64 --self-contained true`, launches the resulting `FSharpQueryStudio.App.exe`, and waits for it to log a new `Host window ready` line — added to `App.axaml.fs`'s `mainWindow.Opened` handler specifically so a black-box test watching the published artifact from outside has *some* signal beyond "the process hasn't crashed yet."

Getting that test itself reliable took three real bugs, not test flakiness to shrug off:
1. Serilog's file sink holds the host log file open with an **exclusive lock for the entire process lifetime**, not just during a flush — confirmed by directly trying to read the file from a second process while the app was running and getting `IOException` every time. A live-polling design (read the file repeatedly while the app runs) can never work against this sink as configured; redesigned to wait a bounded window, kill the process (releasing the lock), *then* read.
2. `File.GetLastWriteTimeUtc`-based filtering to distinguish "this launch's output" from old log content was unreliable — switched to byte-offset diffing (record the file's length before launch, only look at bytes appended after).
3. Fixed by constructing today's exact filename directly (`host-{yyyyMMdd}.log`, matching `RollingInterval.Day`'s naming) instead of globbing at all.

Verified: `dotnet build installer/FSharpQueryStudio.Installer.wixproj` produces a real 75MB `.msi`; `PublishedAppTests` passes twice in a row locally. ## 2026-08-06 — E.3: session-invalidation rules on script edit

The plan's own example — "editing an already-executed cell invalidates from that point forward" — is notebook-cell language, but E.4's `// %%` cell parsing doesn't exist yet, and `ShellViewModel.RunAsync` (as of E.2) always sends the whole document as one `Source` string per run. Asked which rule to build against that reality before writing any test, since more than one reasonable answer exists (invalidate on any edit at all; invalidate on anything but a pure append; or defer the policy question entirely and land only the tracking plumbing). Chose prefix-based: a session invalidates unless the new run's source starts with exactly what it last ran. It's the closest textual stand-in for "everything already executed stays valid, only the new tail is unproven" without real cell boundaries, and it matches how the product actually calls `execution/evaluate` today (the whole growing document, not disjoint snippets) — E.4 can later swap the whole-document text for a specific cell's text and reuse the same rule unchanged.

`SessionStore.getOrCreate` grew a required `source` parameter and now tracks a `LastSource` alongside each `Session`; `SessionStore.invalidates lastSource newSource = not (newSource.StartsWith(lastSource))` is exported as its own pure function so `SessionStoreTests.fs` can codify the rule as plain `[<Theory>]` string cases (unchanged / pure append / first-ever-run all valid; edited, truncated, or unrelated text all invalidate) independent of ever spinning up a real `FsiEvaluationSession`. `Handlers.runEvaluate` now threads `evalParams.Source` through to `getOrCreate`, so a request whose text isn't an append of what its `SessionId` last ran transparently gets a fresh session instead of reusing a stale one — no new worker-visible behavior to wire, since the invalidation happens inside the same call that was already creating-or-reusing.

E.1's own persistent-mode tests broke under the new rule and needed real fixes, not just call-site patches: they'd modeled "Persistent mode" as two independent snippets sent back to back (`"let x = 41"` then `"x + 1"`), which is *not* a pure append and would now (correctly) invalidate — closer to a future Run-Selection/notebook-cell workflow than to what `ShellViewModel.RunAsync` actually does today. Rewrote them to send the accumulated whole-document text each round (`"let x = 41"` then `"let x = 41\nx + 1"`), which is both what E.3's rule requires *and* a more faithful test of the real current wiring. Same fix applied to the equivalent `Worker.Tests`/`Integration.Tests` persistence cases from E.1/E.2, which exercise the same `SessionStore.getOrCreate` call path.

Proving invalidation actually *happened* — not just that the rule function returns `true` — needed a three-round test, not two: a two-round "edit invalidates" test can't distinguish "the old session was dropped" from "the edited text just happens to be self-consistent either way," since re-declaring a `let` binding produces the same visible result whether the session is fresh or reused. `EvaluationTests.fs`'s new case defines `x` and `y` in round 1, edits round 2 to drop the `y` line entirely (invalidating), then round 3 appends a bare reference to `y` onto round 2's surviving text — round 3 only fails (undefined `y`) if round 2 actually got a fresh session with no memory of round 1's `y`; a regression that silently kept reusing the old session would make this test fail by round 3 unexpectedly *succeeding*.

Full solution green: `Execution.Tests` 24 (+9: 6 `SessionStoreTests` theory cases plus a fresh no-reuse case, 1 rewritten and 1 new `EvaluationTests` case), `Worker.Tests`/`Integration.Tests` unchanged in count (existing E.1/E.2 cases updated in place, not added to).

## 2026-08-06 — E.4: notebook `// %%` cell parsing and ordered incremental cell execution

Hit a real design conflict with E.3 before writing any code: "later cells see earlier cells' bindings only within a persistent/notebook session" only means something if each cell is sent as its own isolated text per call (relying on the live session to remember earlier cells) — but that's not a prefix-append of the previous call, which is exactly what E.3's `SessionStore.invalidates` rule, built minutes earlier in this same session, was designed to reject as an edit. A cumulative-resend workaround (send `cell1`, then `cell1+cell2`, ...) would have kept `SessionStore` untouched, but Isolated mode would then also "see" earlier cells (they're baked into the resent text every call), which can't actually prove the acceptance criterion. Asked which way to go; chose to generalize `SessionStore` properly.

`SessionStore`'s `Entry` now tracks `LastFragments: string list` instead of a single `LastSource: string` — an ordered execution log, with two different update policies over the same log: `getOrCreate` (whole-document mode, F5 Run, unchanged since E.1/E.3) always replaces the log with `[source]`, applying the existing prefix-invalidation rule against the log's last entry. The new `appendFragment` (notebook/cell mode) always grows the log by one and never invalidates — a genuinely new, unrelated cell isn't an edit of anything already executed, so there's nothing to invalidate; it's what actually lets cell 2 see cell 1's bindings. Both policies share the same underlying `sessions` map, so a key touched by one is visible to the other (tested explicitly: `appendFragment` then `getOrCreate` on the same key reuse the same session, proven with a genuinely new `Cell` type — a check that only makes sense once both code paths share state, not two disconnected mechanisms bolted together).

`FSharpQueryStudio.Analysis.NotebookCells.parse` splits source text at `// %%` boundary lines (bare or titled, e.g. `// %% Cell 2`) into an ordered `Cell list` (0-based `StartLine`, matching `Diagnostic`'s existing Monaco-facing convention). Handles the edge cases a naive split-on-marker would get wrong: a marker as literally the first or last line, or two markers back to back, all correctly produce no empty cell for that gap rather than an empty string masquerading as one; CRLF and LF both normalize the same way. Pure text splitting only — no FSI, no session concept — `Analysis` stays exactly what Section 4 says it is.

Wiring the two together needed no new protocol method, worker handler, or UI command: the plan's own test-location note (`Analysis.Tests`, `Integration.Tests` — no `Worker.Tests`, no `Protocol.Tests`, no `Ui.Tests`) was the tell that E.4 is proving the *mechanism*, not shipping a "Run All Cells" button yet. `NotebookExecutionTests.fs` parses a two-cell script (`let x = 41` / `x + 1`), runs each cell through `SessionStore.appendFragment` + `Evaluation.evaluate` in order under one key, and asserts the second cell's result is `42` — paired, same convention as every other Isolated/Persistent test in this milestone, with a second case that runs the same two cells through independent `FsiSession.create` calls (no shared session) and asserts `x` comes back undefined, proving the first case's success is actually conditioned on session sharing rather than an artifact of the script itself.

Full solution green: `Analysis.Tests` 29 (+12), `Execution.Tests` 28 (+4: `appendFragment` creation/reuse/reset/shares-state-with-`getOrCreate` cases), `Integration.Tests` 43 (+2).

The architecture doc gives this one line ("add `.fsproj`/multi-file workspace support later") with no schema. ## 2026-08-07 — Fix: UI-Foundation.12's `DockSerializer.Serialize` threw on every real layout

Code review (real reflection/repro, not assumed) found the composition-root wiring above was correct but `DockSerializer().Serialize(mainWindow.MainDockLayout)` threw `JsonException: A possible object cycle was detected` on every real layout — the `try`/`with` around it caught it silently, so `DockLayout` was written as `null` on every close and the whole feature was dead code despite the green build/tests (nothing in the suite exercised real serialization against a real layout).

Root cause, confirmed by reflecting over the installed package's real source (GitHub) and reflecting over the built `Dock.Model.Mvvm.dll`: `IDockable.Owner` (the back-reference to a dockable's parent) is a plain `[DataMember]`, not `[IgnoreDataMember]` — every non-trivial layout has a real cycle through it (child → `Owner` → parent → `VisibleDockables` → child). `DockSerializer`'s options do set `ReferenceHandler.Preserve`, but its own `JsonConverterList<T>.Write` serializes each list element via a *nested* `JsonSerializer.Serialize(writer, item, options)` call, and each nested call starts its own independent reference-tracking scope — so `Preserve`'s cycle protection never spans a list boundary, and every real tree (which is nothing but list boundaries) blows past `MaxDepth` 64 and throws. Confirmed via a throwaway `dotnet fsi` script that built a real `DockFactory` layout exactly the way `MainWindow`'s constructor does and called `DockSerializer().Serialize<IDock>` on it directly — reproduced the exact exception every run, no newer package version exists on NuGet, and the alternate `Save<T>(Stream, T)` method threw identically (same code path).

Fix, in a new `LayoutSerializer` module (`src/FSharpQueryStudio.Ui/LayoutSerializer.fs`): `Owner` is fully redundant on the wire (`IFactory.InitLayout` already reconstructs it after every deserialize, the same call `MainWindow`'s constructor makes on a freshly-built layout), so it's stripped from the JSON via a `JsonTypeInfo` modifier attached to the package's own polymorphic type resolver (`DockModelPolymorphicTypeResolver` — `internal` to the package, but derives from the public `DefaultJsonTypeInfoResolver`, so an instance obtained via `Activator.CreateInstance` still exposes the public `Modifiers` list needed, without having to reimplement the resolver's `$type`-discriminator handling from scratch).

That fix alone wasn't sufficient: with `Owner` stripped, `Serialize` succeeded structurally but then failed inside `ScriptDocument.Document` (an `FSharpQueryStudio.Protocol.SessionMode` F# DU, which plain `System.Text.Json` can't serialize) — and even after excluding that property too, `Deserialize` failed separately with `InvalidOperationException: ... constructor ... must bind to an object property or field`, because `ScriptDocument` has only a 3-argument constructor (`document`/`shell`/`editorContent` — none of which exist as plain JSON data) and can never be reconstructed by System.Text.Json's default object-converter, regardless of what properties are included or excluded. This isn't a bug to route around — a document tab's content was never going to survive a restart anyway, same reason `ScriptDocument.Context` (the shared WebView) is already `[IgnoreDataMember]`. So `DockFactory` gained two new members: `SerializeLayout` (temporarily empties `documentDock`'s tab content for the one `Serialize` call, then restores it immediately — the live, still-open tabs are completely unaffected) and `RestoreDocumentTabs` (after a successful deserialize, finds the now-empty `documentDock` placeholder in the restored tree by `Id` — a plain `[DataMember]` string that does round-trip — and splices the live `documentDock` back in place of it, so the restored layout shows the real open tab(s) instead of a blank document pane). `App.axaml.fs` calls both: `SerializeLayout` on `Closing`, and `RestoreDocumentTabs` (followed by a second `InitLayout` to re-wire `Owner`/`Factory` on the grafted node) right after a successful `Deserialize` at startup.

All of this was verified against a *real* `DockFactory` layout via throwaway `dotnet fsi` scripts before being turned into production code and a real xunit regression test — not assumed to work from reading the stack trace. Added `LayoutSerializerTests.fs` to `Ui.Tests` (3 tests, same "build a real `DockFactory` layout" pattern `DockFactoryTests.fs` already uses): `Serialize`-then-`Deserialize` doesn't throw; a `Proportion` change on a tool pane (`ResultsDock`/`WorkspaceDock`) survives the round-trip; `RestoreDocumentTabs` grafts the live `DocumentDock` back and the restored document tab is the same `ScriptDocument` with the same `Document.Uri`.

## 2026-08-10 — Final-review fix wave: three Task 14 gaps closed, plus the post-save editor re-key

The whole-branch re-review after UI-Foundation.14 turned into a real fix wave (`31dfc9c`, `7f7c3c6`, `6b0e847`, and this entry's own commit). **Three claims in the Task 14 entry above are now out of date and are corrected here rather than edited in place, so the acceptance pass stays a faithful record of what was true on 2026-08-07:**

- **"F5 is not actually bound anywhere"** — it is now. `MainWindow` adds a window-level `Window.KeyBindings` entry (`KeyGesture(Key.F5)` → a minimal internal `RelayCommand` calling `RunAsync`), landed in `7f7c3c6`. Avalonia ships no relay-command type and a `KeyBinding` can only invoke an `ICommand`, hence the small adapter. The menu item's `InputGesture` only ever *rendered* the "F5" text; the window binding is what actually fires it.
- **"Saving an `untitled:` tab never renames the tab's `Uri` or clears `IsDirty`"** — it does now, via `DocumentViewModel.MarkSaved` (`31dfc9c`), with `ScriptDocument` re-keying its `Id`/`Title` off the `Uri` change. A second Save on the same tab writes straight through instead of re-prompting. `7f7c3c6` also made every save route through a `tryWriteFile` helper that logs a warning and reports success, so `MarkSaved` only runs on a write that actually landed — a failed save can no longer clear the dirty marker and tell the user their work is safe when it isn't.
- **"`ConfirmDiscardDirtyDocument` stays `None` in the running app"** — it is wired now (`7f7c3c6`). `MainWindow` supplies a real confirmation dialog: Avalonia ships no message box, and Dock needs a synchronous `bool` back from `ScriptDocument.OnClose()`, so it's a small owned `Window` pumped on a nested `DispatcherFrame`. Cancel is the default/cancel button, and any failure to show the dialog keeps the tab — the safe answer is always the one that doesn't discard work.

The same wave also fixed: closing the last document tab leaving the document area empty while `ActiveDocument` pointed at an invisible replacement; File > New/Open tabs added straight to `VisibleDockables` keeping a null `Owner`, which made them impossible to close at all; `RouteTextChanged` routing editor `textChanged` messages by URI instead of at `ActiveDocument` (a cross-tab corruption once more than one tab could be open); `NextUntitledUri` probing for a free name instead of `Documents.Length + 1`; `UiState.read` crashing startup on a `ui-state.json` holding literal JSON `null`; `Material.Icons.Avalonia` never having its control theme registered, so all seven toolbar icons rendered blank; and a Section 5 claim that floating-window state survives a restart, which it does not.

**This entry's own fix — the interaction between two of those.** `RouteTextChanged` now matches strictly on the URI a message carries, and `MarkSaved` retags an `untitled:` document to its real path. But `editor-host.html` keeps its *own* `documentUri` variable, updated only when a `documentLoaded` message arrives, and stamps every outgoing `textChanged` with it. Nothing pushed `documentLoaded` after a save — `MainWindow` only pushed one on `DocumentActivated` (tab switch), and retagging `ScriptDocument.Id`/`Title` doesn't raise that event. So after the first save of a new file the page kept tagging keystrokes with the dead pre-save URI, `RouteTextChanged` matched nothing, and every edit was dropped in silence: File > New → type → Save → keep typing → Save again wrote the **pre-save** text, and the tab never even re-marked dirty to hint anything was lost. Fixed by routing all three save paths through a new `ShellViewModel.MarkDocumentSaved(doc, newUri)`, which wraps `MarkSaved` and pushes `DocumentLoaded(doc.Uri, doc.Version, doc.Text)` through the existing `SendToEditor` hook **when the URI actually changed and the saved document is still the active tab**. Both guards are deliberate. `documentLoaded` calls Monaco's `setValue`, which discards the editor's undo stack, so re-pushing on an ordinary same-path re-save would cost the user their undo history for nothing. And the save handlers `await` a file picker, so the user can switch tabs before the write lands — pushing then would re-key the page onto a document it isn't showing *and* overwrite the visible tab's text with the saved one's. That background case needs no push anyway: switching back raises `DockFactory.DocumentActivated`, which pushes the by-then-retagged URI itself.

Putting the wrapper on `ShellViewModel` rather than inline in `MainWindow` is what makes the bug testable at all — `MainWindow` isn't unit-testable in this codebase (it needs a real `DockControl`/WebView), but `SendToEditor` is already a composition-root hook a test can capture, the same seam `ProblemViewModel.Navigate`'s tests use.

Verification: 5 new `ShellViewModelTests` (URI-changing save pushes a well-formed `documentLoaded`; an edit typed after the save reaches the document end to end; a same-URI re-save pushes nothing; a save for a tab that's no longer active pushes nothing; no editor hook configured still marks clean and doesn't throw). Beyond the tests, a `dotnet fsi` probe stood a fake editor page next to a real `ShellViewModel` — a `pageUri` variable updated *only* on `documentLoaded`, exactly as the JS does — and ran the reported sequence both ways. Before (`doc.MarkSaved` alone): page URI stuck at `untitled:Script1.fsx`, second save wrote `"let x = 1"`, dirty flag `false`, post-save edit lost. After (`vm.MarkDocumentSaved`): page URI moved to the saved path, second save wrote `"let x = 1\nlet y = 2"`, dirty flag `true`, edit kept. The Monaco half of the round trip (`setValue` actually re-keying the live page) is still not testable here — no JS harness, no headless WebView — and stays on the user's manual list, same as every prior `editor-host.html` change.

## 2026-08-10 — Fix: script pane rendered as an empty black rectangle, no Monaco visible

Reported directly by the user running the built app for the first time: the document pane was just the dark-theme background, no editor, no cursor, nothing to click into. Not a focus/input bug as first suspected — Monaco was never on screen to receive input at all.

**Root cause.** `ScriptDocument`/`Tool` (Task 5/6/11) correctly place the shared `NativeWebView`/`ResultsView` in `Context: obj`, since `Dock.Model.Mvvm.Controls.Document`/`Tool` have no `Content` property (confirmed by reflection back in Task 5). What none of those tasks' empirical API investigations turned up — because nothing that far into the branch had a display to check against — is that `Dock.Model.Mvvm`'s dockables don't host whatever's in `Context` directly either. Dock resolves a dockable's on-screen content through an `IDataTemplate` lookup keyed by the dockable's own type, the same mechanism WPF/Avalonia `ContentPresenter`s use for arbitrary view models — `Context` is data to be templated, not a control to be hosted. `DockControl.AutoCreateDataTemplates` (on by default) supplies *some* default template, but it has no idea `Context` here happens to already be a built `NativeWebView`/`ResultsView`, so it renders nothing. Every prior review pass (including the final whole-branch review, which explicitly flagged this exact risk as unverifiable without a display) had no way to catch it — `dotnet build`/`dotnet test` don't exercise Avalonia's template-resolution pipeline at all, and the app launches and reaches "Host window ready" whether or not anything is actually drawn inside the dock panes.

**Fix.** `MainWindow.axaml.fs` registers two `FuncDataTemplate`s on the real `DockControl` before `Layout` is assigned — one for `Dock.Model.Mvvm.Controls.Document`, one for `Tool` — each producing a `ContentControl` whose `Content` is the dockable's own `Context`. Avalonia's `ContentPresenter` recognizes that value is already a `Control` and hosts it directly rather than looking for a further template, so the `NativeWebView`/`ResultsView` instances built in `MainWindow`'s constructor finally reach the screen. Registered ahead of whatever `AutoCreateDataTemplates` supplies so these are the first match Avalonia's template lookup finds for either type.

**Also added while chasing this, at the user's request as a diagnostic:** every freshly created document (the workspace's very first tab and every `File > New`) now seeds with a short F# comment + `printfn` example instead of an empty buffer, so a blank pane and a genuinely-empty-but-rendering editor are no longer visually identical. `DocumentViewModel` gained an optional `initialText` constructor parameter that sets `Text` directly — bypassing `ApplyTextChanged` — so the seed doesn't mark a freshly opened tab dirty for text nobody typed; `Version` stays `0`, matching Monaco's own `currentVersion` on a fresh load, so the guard in `ApplyTextChanged` still accepts the user's first real edit normally.

Three pre-existing `ShellViewModelTests` asserted a second/background/orphaned document's `Text` was `""` — true before this change, no longer true now that every document starts with seed text. Updated to capture the untouched document's text before the exercised operation and assert it's unchanged, rather than asserting a specific literal — the tests' actual intent (routing doesn't touch documents it shouldn't) is unaffected either way.

Build/test: `dotnet build` clean, 0 warnings, 0 errors, full solution. `dotnet test`: same 12 pre-existing Testcontainers/Docker-unavailable failures as every prior round (`Integration.Tests` only, unrelated to this change), everything else green — `Ui.Tests` 135/135.

**Still unverified in this environment, same standing limitation as every prior XAML/WebView task:** that the icons/editor/results actually render correctly on a real screen. The mechanism (an `IDataTemplate` match producing a `ContentControl` around an already-built `Control`) is standard, well-documented Avalonia behavior and not itself risky, but this fix is the first change in the whole branch that could only have been found by someone actually looking at the running app — worth remembering for UI-Workspace: `Avalonia.Headless` rendering tests would have caught this class of bug automatically instead of shipping it to a user's first launch.

## 2026-08-10 — Fix: the shared `NativeWebView` design itself was broken — one instance per tab instead

The `DataTemplate` fix above got Monaco on screen, but the user's very next report — still nothing visible, plus `InvalidOperationException: The control NativeWebView already has a visual parent ContentPresenter ... while trying to add it as a child of ContentPresenter ...` the moment a second tab was opened or closed — pointed at something deeper than a missing template.

**Root cause.** Every `ScriptDocument`'s `Context` was, by design since Task 5, the *same* single `webView` instance — the whole rationale being "one Monaco/WebView2 engine, not N of them." That's a fine instinct for the underlying browser engine, but it collided with how Dock actually presents document content: each `ScriptDocument` gets its own `ContentControl` (one per open tab, built by the `FuncDataTemplate` above), and Avalonia's visual tree requires a `Control` to have exactly one parent. The instant two `ScriptDocument`s existed — which `CreateLayout`'s one initial tab never triggered, so nothing caught this in Task 5-9's own work — both tabs' `ContentControl`s tried to claim the identical `NativeWebView`, and the second claim threw. This is exactly the residual risk flagged (but not yet forced to a head) in the final whole-branch review: *"Shared NativeWebView across N ScriptDocument.Context values is safe only while document-tab caching is off ... enabling it ... would throw the moment a second tab opens."* Turns out no caching setting was needed to hit it — Dock realizes more than one tab's content control under ordinary add/remove, not just under an opt-in caching feature.

**Fix.** `DockFactory`'s constructor now takes `createEditorControl: unit -> obj` instead of a fixed `editorContent: obj` — a factory, not an instance. `MainWindow` supplies a closure that builds a brand-new `NativeWebView`, points it at `editor-host.html`, and wires its own `WebMessageReceived` handler, and `DockFactory` calls it once per tab (`CreateLayout`'s initial document, and `addTab` for every `File > New`/`Open` after). `DocumentActivated` now fires the `ScriptDocument` itself rather than just its `DocumentViewModel`, so `MainWindow` can reach that specific tab's own `Context` to push its `DocumentLoaded` notification into the right control — there's no longer a single webview to default to. `ShellViewModel.SendToEditor` (shared by `ProblemViewModel.Navigate` and the post-save re-key) now resolves to whichever tab is active *at send time* via `dockFactory.DocumentDock.ActiveDockable`, since both callers only ever act on the active document and there's no longer one fixed webview to reach directly.

`ResultsView` stays shared — there's exactly one "Results" tool in the whole app, never two competing for the same control, so nothing about it needed to change.

**Known cost, not fixed here:** switching back to an already-open tab still re-pushes `DocumentLoaded` (same as before this change), which calls Monaco's `setValue` and discards that tab's undo stack and cursor position — the pre-existing Minor finding from the final review. Per-tab `NativeWebView`s make "only push once, on first activation" straightforward to add later (each tab now keeps its own live Monaco state across switches once loaded), but that's a UX improvement, not what was crashing — left for a follow-up rather than bundled into an urgent fix.

New regression test: `every open document tab gets its own editor control instance, never shared` (`DockFactoryTests.fs`) — a `DockFactory` built with a counting `createEditorControl`, three tabs opened, asserts three distinct contexts. ## 2026-08-10 — Fix: the custom `DataTemplate` fix was targeting the wrong thing entirely — `IDocumentContent`/`IToolContent` were the real contract

Third report in a row on the same underlying symptom: even after the shared-`NativeWebView` crash was fixed, Monaco still never appeared. This time the fix required actually loading `Dock.Avalonia.dll` (the real UI control package, not the `Dock.Model`/`Dock.Model.Mvvm` layers every earlier investigation in this project had reflected on) and calling its internal rendering logic directly, rather than reasoning from documentation snippets a third time.

**Root cause, found by direct experiment, not by reading further docs.** Loaded `Dock.Avalonia.Internal.DockDataTemplateHelper` (the class behind `DockControl.AutoCreateDataTemplates`, on by default) and called `CreateDefaultDataTemplates()` for real. The very first template in the list targets `Dock.Model.Controls.IDocumentContent` — a genuine interface with a real, settable `Content: obj` property — and `Match()` against a plain `Document` with only `Context` set returns `false`. `Dock.Model.Mvvm.Controls.Document` does not implement it. Confirmed with a second probe: a test type implementing `IDocumentContent.Content` matched immediately and built a real `Dock.Avalonia.Controls.DocumentContentControl`. The earlier `FuncDataTemplate<Document>`/`<Tool>` registration (previous entry) was a plausible-looking fix that happened to compile and run without error, but was never the mechanism Dock's own `DocumentContentControl`/`ToolContentControl` machinery actually consults — which is exactly why nothing changed after it shipped.

**Fix.** `ScriptDocument` now implements `Dock.Model.Controls.IDocumentContent`, returning its `editorContent` (unchanged from before) through `Content` instead of `Context` — `Context` is no longer set at all, and `EditorControl` is a new plain member exposing the same object for `MainWindow`'s own bridge-push code, so nothing there needs an interface cast. A new type, `ContentTool`, does the equivalent for the "Results" tool: `Tool` itself can't be extended with a constructor-injected `Content` (its own persistence needs a parameterless constructor — see below), so `ContentTool` is a small subclass with a plain settable `Content` property, `[<IgnoreDataMember>]` for the same reason `DockableBase.Context` already carries that attribute (a live `ResultsView` can't be JSON-serialized — this is the identical failure class Task 12 spent four rounds fixing for `Context`, now avoided up front for `Content`). The hand-rolled `FuncDataTemplate` registrations from the previous fix are removed entirely — `AutoCreateDataTemplates`'s real defaults now do the work, which is what they were always meant to do.

**The one thing this could have broken and didn't:** `ContentTool` is a genuinely new concrete type entering the serialized layout for the first time — unlike `ScriptDocument`, which is structurally excluded from the wire format, `resultsTool` *is* part of the normal persisted layout, restored by `DockFactory.RestoreToolPanes`'s `FindById` lookup. Whether Dock's polymorphic serializer would preserve a custom `Tool` subclass's concrete type through a real round-trip was untested territory. It works: `RestoreToolPanes`'s existing pattern match now requires the restored node to come back as `Some(:? ContentTool as rrt)` rather than accepting any `IDockable`, and the full existing `LayoutSerializerTests` suite — unmodified in its actual assertions, only in the `.Context` → `.Content` property it reads — passed without a single new failure. If the concrete type hadn't survived, the match would have fallen through to `RestoreToolPanes` returning `false`, the same safe "reject this restore, fall back to the default layout" path every other restore failure in this project already degrades into — not a crash.

Three pre-existing tests needed the same mechanical `.Context` → `.EditorControl`/`.Content` rename this fix's own interface change required (`ScriptDocumentTests.fs`, `DockFactoryTests.fs`, `LayoutSerializerTests.fs` — six call sites across the latter, all reading `factory.ResultsTool.Context`), plus one new test added directly: `IDocumentContent.Content is the same editor control instance EditorControl returns`.

## 2026-08-10 — Diagnostics: `AssetHost` never logged its own port or an accept-loop death

User report: `http://127.0.0.1:PORT/` unreachable in a browser while the app was running, suspecting the Monaco asset host wasn't actually running. Investigated directly rather than guessing: built and launched the real app, read the (until now, nonexistent) startup log for the bound port, and `curl`'d it live while the process was still up.

**Findings, empirical, not inferred.** `GET /editor-host.html` → `HTTP 200` with real content; `GET /` → `HTTP 404` (correct — the loopback server only serves known files under `EditorAssets`, by design since A.11). The asset host works exactly as intended. The far more likely explanation for the report: `AssetHost.start` picks a fresh OS-assigned ephemeral port on every single launch, and — until this entry — logged nothing about which port that was. Whatever address the user tried was almost certainly captured from a prior run; once that process exits, nothing is listening on that port anymore, and there was no way to tell "stale port" from "the listener is actually broken" after the fact.

**Fix — pure observability, no behavior change.** `AssetHost.start` now logs `Asset host listening at {BaseUri}` (`Log.Information`) the moment the real listener starts. `acceptLoop`'s catch clause previously handled exactly two exception types (`ObjectDisposedException`/`HttpListenerException`, both normal shutdown signals) and let anything else silently end the loop with zero trace — any other exception now gets `Log.Warning`'d before the loop still stops the same way it always did. Needed adding `Serilog` as a direct dependency of `FSharpQueryStudio.Editor` (it had none before), matching the same direct-`Log.*`-call convention already used in `Worker`/`Ui`/`App` rather than routing through `ILogger<T>`.

**Also surfaced while reading the log, unrelated to this report but worth recording:** the user's last two real launches (before this session's rebuilds) both logged `Saved dock layout passed CanRestore but a graft still failed; using the default layout instead`. Expected, not a new bug — their `ui-state.json` was written by a build from before the `IDocumentContent`/`ContentTool`/shared-`NativeWebView` fixes landed, so the saved object graph no longer matches what the current `DockFactory` builds. `CanRestore`'s whole job (Task 12) is exactly this: reject an incompatible saved layout and fall back to the default rather than corrupt anything. Confirmed safe, not investigated further.

## 2026-08-10 — UNRESOLVED: real content in the dock layout crashes the app with a StackOverflowException

**Status: blocked, not fixed.** After the `IDocumentContent`/`ContentTool` fix (previous entry) made the document/results panes render for the first time, the user reported a new, severe symptom: the app throws a fatal `StackOverflowException` a few seconds after launch. This entry documents everything ruled out so far, so the next attempt doesn't repeat this investigation from scratch.

**The crash is real and reproducible.** `StackOverflowException` is uncatchable in .NET — nothing in the app's own Serilog output can show it, and it never reached Windows Event Log either (checked directly; the only recent fatal-crash event in Event Viewer belonged to an unrelated process). Reproduced directly instead: launched the built app with a bounded timeout and captured raw console output. Every crash shows the identical shape — `Avalonia.Layout.LayoutManager.Arrange(Layoutable)` calling itself thousands of times (7000+), then unwinding through `ExecuteArrangePass` → `ExecuteLayoutPass` → `MediaContext.Render` → the normal dispatcher/message loop. This is Avalonia's own layout system in unbounded self-recursion, not anything in this project's application code throwing.

**Ruled out, each via a real rebuild-and-relaunch test, not reasoning alone:**
- **Not `NativeWebView`.** Swapped `createEditorControl`'s return value for a plain `TextBlock` — identical crash, identical stack shape.
- **Not `ResultsView`/`DataGrid`.** Additionally swapped `resultsView` for a plain `TextBlock` (both controls stubbed at once) — identical crash.
- **Not Dock's own `DocumentContentControl`/`ToolContentControl`.** Registered a custom `FuncDataTemplate<ScriptDocument>`/`<ContentTool>` producing a plain `ContentControl` instead, bypassing Dock's default `IDocumentContent`/`IToolContent`-driven templates entirely (confirmed via the same `DockDataTemplateHelper.CreateDefaultDataTemplates` reflection from the previous entry that these two are what `AutoCreateDataTemplates` actually builds) — identical crash, real `NativeWebView`/`ResultsView` content, same `LayoutManager.Arrange` recursion.
- **Not the asset host / browser interaction the user described.** The crash reproduces with a bounded, non-interactive launch — no browser involved, no request ever reaches `AssetHost`. The "address unreachable" report from the previous entry and this crash are two separate, unrelated symptoms that happened to be reported together.

**What's left, not yet tested:** the surrounding `ProportionalDock`/`DocumentDock`/`ToolDock` nesting `DockFactory.CreateLayout()` builds (horizontal outer split, vertical inner split, `Proportion` values 0.2/0.3, `IsCollapsable = false` on several nodes) is the one variable never isolated — every test so far changed *what* renders inside a pane, never the dock structure itself. A minimal single-pane layout (just `DocumentDock`, no workspace/results panes, no nesting) with real content would either implicate the nesting specifically or rule it out too.

**Also checked and ruled out as an easy fix:** `Avalonia.Controls.WebView` is pinned at 12.0.1 against the rest of Avalonia's 12.1.1/Dock's 12.1.0 — a real version gap, but no 12.1.x release of that package exists yet on NuGet, and the `NativeWebView`-removed test above crashes identically anyway, so this isn't the cause. Found one related, still-open, unfixed upstream report — [wieslawsoltes/Dock#1102](https://github.com/wieslawsoltes/Dock/issues/1102), "InvalidOperationException when using ContentControl inside DocumentDock" — describing Dock 12.x's content-hosting as fragile in ways Dock 11.x wasn't (no comments, no fix). No existing upstream issue matches this specific StackOverflow/Arrange-recursion shape; worth filing one if this remains unresolved, since it may be new information for that project.

**Current code state:** left relying on `AutoCreateDataTemplates`/`IDocumentContent`/`IToolContent` (the architecturally correct approach from the previous entry, not disproven, just insufficient on its own) rather than the custom-`ContentControl` mitigation, since the latter didn't help and added complexity for no benefit. The app still crashes in this state — this entry does not claim a fix, only documents the elimination work done so far.
