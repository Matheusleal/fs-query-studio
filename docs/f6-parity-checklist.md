## Findings

- **Row 4 — the one parity criterion not met at F6 close.** Connection-name string-literal autocomplete (`Connections.sql "…"`) regressed when `src/FSharpQueryStudio.Ui/ConnectionNameCompletion.fs` was deleted in F6.2. The extension has no replacement provider (`editors/vscode/src/lang/providers.ts` only forwards generic FSAC identifier completion; the worker's FSAC prologue injects `Connections`/`Results` *definitions*, not connection-name string literals), and F6's spec forbids extension feature work, so it is recorded here and moved to the F7 backlog rather than reimplemented. The other seven F6 criteria remain met.
- **Row 6 — one spec assertion fails on Windows only, green in CI.** `connections.test.ts` "resolves a `{password}` token from SecretStorage over the reverse channel" fails its *final* assertion locally on Windows: `message.includes(sentinel)`. The test's own comments label this "KNOWN NPGSQL VARIANCE" — some Npgsql builds report `"No such host is known."` without echoing the resolved host. The **guaranteed** bridge proof earlier in the same test (`!message.includes("{password}")` — the literal token was substituted by a value fetched over `secret/get`) passes locally, so the reverse secret bridge is proven to run. The full spec runs green in `.github/workflows/vscode-extension.yml` (Linux, `xvfb-run`), which fires on every push to `main-vscode` and is the stated merge gate. Not a parity gap.
- **Row 8 — the original design's second OutputChannel is not built on `main-vscode`.** The migration design envisaged both a `"F# Query Studio"` and a `"F# Query Studio (Worker)"` channel (and an `src/log/channel.ts` module); on `main-vscode` only the single `"F# Query Studio"` channel exists, created inline in `src/extension.ts`. The parity criterion (in-app log viewer downgraded to an OutputChannel + the worker's Serilog file sink, no in-app viewer) still holds — the Row 8 Evidence cell above records only what is present. The missing second channel is ruled F7 backlog, not an F6 parity gap.
- **Not a checklist row, but observed:** `intelligence.test.ts` "reports a diagnostic for a broken edit" fails locally (no diagnostic surfaced within the 30 s poll). This is a *second* intelligence spec, separate from the Row 4 completion criterion (which passes). It exercises the diagnostics-on-edit path, a known-fragile area per the F4 DEVLOG (cell diagnostics go stale / lag on upstream edits). It gates in the `vscode-extension.yml` CI run. Flagged for the reviewer; outside the F6 parity list.
